# 状态与证据

项目保留一个 `.retro/`。每项工作的过程记录放在 `.retro/goals/<记录ID>/`，下文称“目标目录”。PROGRESS.md、RUNBOOK.md、runbook/、实验方法和结果均绑定目标。相关新目标可以明确引用旧方法，但先核对版本、数据和适用条件；确认可跨目标复用的知识再整理进项目正式文档。

## 选择目标记录

先核对原生 goal 和最新用户指令，用 `retro.mjs records show --session <主会话ID>` 查看当前绑定的记录 ID、目录和目标。hook 首次看到新目标时创建独立目录。按这个目录读取进度与证据。

目录名为 UTC 创建日期加 8–12 位十六进制 ID，例如 `20261021-7c2f8a91`。目标名称写进 PROGRESS 标题和正文，措辞变更不用重命名目录。脚本把会话、原生目标身份与目录关联；修改时间和文字相似度不能决定继承关系。

| 用户意图 | 记录处理 |
|---|---|
| 进行中的目标微调，或恢复同一项未完成工作 | 原生目标身份不变时沿用目录；身份变了但仍是同一工作时，用 `records use <记录ID> --session <主会话ID>` 显式关联原目录 |
| 原目标完成后追加相关工作 | 使用新目录，保留旧目标最终快照；只摘取适用的成果与证据并写明来源 |
| 相近目标但数据、评价标准或主要约束变化 | 主 agent 判断是否仍属同一工作；采用新目录时只继承核实过的内容，旧结果不能直接证明新目标达成 |
| 本质不同的新目标 | 使用新目录；若平台沿用了原生身份，用 `records new --session <主会话ID>` 切换 |

主 agent 根据用户意图和实际变化判断延续关系，简短说明沿用什么、什么需要重验。意图明确时直接处理；只有歧义会明显改变工作范围时才询问。脚本不做语义相似度判断，也不自动复制旧目录。切换前让旧执行者交回或停止；仍在交付的执行者和评审使用原来的绝对目录，迟到报告留在原目标。每次委派传入当前目标原文、记录 ID 和目录绝对路径。

`records use` 只改变目录绑定。关联后更新目标和验收条件，重评受影响的结论、待办和授权事项；保留仍适用的用户长期约束。切换目录会重置该原生目标的读取游标，执行名额和评审请求仍需按实际工作检查。

## 进度快照

目标目录的 PROGRESS.md 保留当前目标、仍有效的用户约束、证据和关键决定，通常约 4 KB；详细过程留在任务笔记。

```text
# PROGRESS：目标名称（YYYY-MM-DD HH:MM）
记录 ID：…
目标（同 /goal）：… · 怎么证明：…
继承来源：记录 ID / 文件 / 证据 · 适用条件 · 需要重验的内容
用户指令：…
最好结果：…（版本、证据）
差距：…（已知事实与待验证假设）
路线：… · 理由：… · 复查条件：…
进行中：任务 — 执行者 / worktree — 资源 — 任务目录
下一步：…（责任人、复查时间或条件）
上次评审：时间 — 结论 — 如何处理
待授权：事项 — 原因 — 提出时间 — 已追问次数
其他：手册、想法池、积压、总表的位置
```

开始、恢复、目标变更和上下文压缩后核对快照与当前目标。关键变化及时写；检查点用 `inbox --session <主会话ID>` 汇集当前记录目录的新结果，整理后用 `done "<决定>" --session <主会话ID>` 标记。旧目标的报告即使刚更新，也不会进入新目录的 inbox。

读取游标、名额、评审请求和显式目录绑定在 `.retro/checkpoints/<会话>/<原生目标开始标识>/`。默认目录由目标身份稳定生成；`goal.json` 保存创建来源。它们由脚本管理，不手改。暂停后恢复同一原生目标保持绑定；新原生目标默认独立，需延续时显式关联。`slots`、`request` 也用 `--session` 指定归属。

## 写入归属

每个目标目录指定一个协调主会话独写 PROGRESS、ideas 和 backlog；交接先让原写入者交回或确认停止，再记录新负责人。不同目标可以在同一项目使用独立目录；同仓库 worktree 共用运行状态，不能因此并发改同一文件。

| 文件 | 写入责任与用途 |
|---|---|
| `<目标目录>/PROGRESS.md` | 该目标的协调主会话独写；方向、决定、用户约束和共享文件负责人 |
| `<目标目录>/RUNBOOK.md` 与 `<目标目录>/runbook/` | 主 agent 指定的唯一合并者；经核实、适用于当前目标的构建、测试、评测方法、参数和代码地图，其他执行者只读 |
| AGENTS.md | 项目规则；长期约束按用户授权和项目惯例维护 |
| `<目标目录>/tasks/<任务>/report.md`、`notes.md`、`results.tsv` | 该任务的执行者独写；回报、细节、评测原始结果及待合并的补充 |
| `<目标目录>/ideas.md` | 协调主会话独写；有价值的想法、知识缺口、死路证据与重试条件 |
| `<目标目录>/backlog.md` | 默认由协调主会话独写；委托整理期间主会话停写，收回权限后再写 |
| `<目标目录>/results.tsv` 或该目标已有总表 | 指定的唯一汇总者；从已交付任务的结果表合并，保留任务、版本、输入和证据来源 |
| `<目标目录>/probes/` 与评审存档 | 后台代理；探测和报告，按登记协议交付 |

想法池不规定数量。合并重复、移除过时项目；用户明确要求试的优先安排。死路保留否定依据，相关条件或评测变化后再查。积压在影响验收或自然里程碑时重评，不为清单本身开启无止境工作。

委托 backlog、手册或总表时，写明具体文件、唯一写入者和交回条件。原写入者停止编辑；它确认交回或已经停止后，才允许下一位写入。委托期间的新发现先放各任务的 notes/report，由负责人合并，不能双方同时改共享文件。任务 ID 在整个项目内唯一，恢复同一任务要先确认原执行者已停止；不同会话和 worktree 不能复用一个仍在写入的任务目录。

评测程序写本任务的 `results.tsv`，同一任务内部并行评测也各写自己的分片文件，由该任务的单一汇总者生成任务表，不并发追加同一个文件。生成中的结果保留在分片或临时文件，完成后再发布；汇总者只合并已交付、不会继续改动的版本，按任务和运行标识去重，保留原始结果。hook、`inbox` 和 `status` 会读取任务表，无需等目标总表合并才发现新结果。

## 手册汇总

执行者在各自任务的 `notes.md` 记录方法、适用条件和证据，回报时指出值得保留的补充，不并行改本目标手册。影响其他任务的发现立即回报主 agent，由它转给相关执行者，不等手册合并。

任务验收、阶段检查点或收尾时，主 agent 按需要指派一名执行者，汇总已交付的笔记到 `<目标目录>/RUNBOOK.md` 及 `<目标目录>/runbook/`。同一时间只有这一名合并者可写；上一位结束或确认停止后才转交。手册与任务笔记均属于当前目标；跨目标引用要注明来源并重验适用条件。合并时去重，核对版本和适用条件，保留任务与证据来源；结论冲突先标待核实并回报，不用后写的直接覆盖。原始任务笔记保留，便于追溯。

合并者回报改了哪些方法、适用范围和具体段落；主 agent 只向受影响的执行者转达。执行者中途继续按需读取本目标手册及获转达的补充，不必等所有任务结束，也不靠定时重读所有手册来发现更新。

## 版本控制

过程记录默认只保存在本地：进度、任务说明、工作笔记、探测报告、评审、想法池和中间结果均不随代码提交。新记录统一放 `.retro/`，包括 PROGRESS.md 和 RUNBOOK.md。需要交付的方法或结论先整理成项目正式文档，不把流水记录直接纳入仓库。

Git 项目在写记录前运行 `retro.mjs init --root <项目绝对路径>`。它将 `.retro/` 加入 Git 本地 `info/exclude`，按项目子目录限定范围，worktree 共用；不改项目 `.gitignore`。仓库规则抵消本地排除时会报错，需要先解决，不能把失败当作已经保护。

忽略规则对已跟踪文件无效，`init` 会列出这些路径。先按内容区分过程记录与正式交付；确认是过程记录后，用精确路径执行 `git rm --cached -- <文件>`（目录加 `-r`），保留本地内容，只取消今后的跟踪，不重写历史。不要把原有项目文档或别人暂存的交付一并移除。

提交前核对 `git diff --cached --name-only`，按具体交付路径暂存；不为保存过程记录而使用 `git add -f`。AGENTS.md 只保留项目规则，任务状态、排错经过和临时发现写入本地记录。

`.retro/` 在 worktree 间共享，委派时给绝对路径并协调写入。其余状态文件由脚本维护，不能手改；`status`、`metrics` 只读，`inbox` 会记录本轮读取时间，`slots`、`request`、`done`、`abort` 等用于显式管理。

进度台 `retro-status` 可以读取快照和任务细节；转达只在用户明确要求时进行。状态记录是观测，不能单凭提交数、日志行数或代理活动断言有价值的进展。
