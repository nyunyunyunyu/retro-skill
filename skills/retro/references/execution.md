# 委派与验证

主 agent 保持调度上下文；执行、探索和深入复盘由子代理完成。委派的粒度要能交回一个有用结果，耗时不确定时先做短探测。

## 任务说明

写明目标和验收标准、负责的文件或范围、相关用户约束、已有事实和证据位置、可用资源、阶段预算、验证范围，以及任务目录的绝对路径。告诉执行者它不是唯一在工作的代理，不要覆盖别人的改动；给出正在运行、不能碰的文件和资源。

让执行者读取本 skill 的 `templates/executor.md`。本次迭代积累的方法默认放 `.retro/RUNBOOK.md`，已有正式手册按项目惯例维护；按任务给相关路径，不复制整段历史。新代理要获得足够上下文；同一问题的追问优先复用原代理。

并行度由任务独立性、机器资源、用户要求和平台能力决定。`retro.mjs slots <N> <理由>` 记录当前计划的执行名额，包含你对等待和资源限制的解释；它不是必须填满的配额。后台评审也消耗平台容量，资源紧张时错开。

阶段预算由任务决定。现有脚本在连续一小时尚未交回时提醒检查，不代表所有任务都必须在一小时内停止。外部 Codex 驱动另有硬超时，见平台接入。

## 验证

选择能支持当前决定的验证，任务说明写清范围和预算。可以用这些档位沟通：

- 探索：足以决定是否继续投入的便宜信号。
- 采纳：覆盖本次改动风险、支撑采用结果的检查。
- 最终：覆盖用户目标与交付要求的完整证据。

用户要求的检查必须保留。同一版本、输入和环境已有有效结果时复用；新变化或证据不足才补测。高后果或新的最佳结果可独立核实，确定性实验优先核对方法和代表性复现，不机械重复整套。

问题按对目标的影响处理：会使结果错误或阻止达成的及时修；其他问题与主工作一起处理，或放入积压。不要让低影响发现不断生成新的验证工作。修改评测后，重新检查依赖旧评测的结论。

## 回报与验收

收到回报时，先看结果、证据、阻塞和推翻前提的观察，再决定验收、追问、继续或换人。只做短的证据核对；需要读长日志或复现实验就委派核实。

原代理申请继续时，按已经获得的进展、剩余价值和成本决定，不自动续期或自动换人。下一项任务不必抢在用户输入和重要回报之前派出。
