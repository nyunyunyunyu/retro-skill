# 瓶颈分析

收到慢调用提醒、验证预计超预算，或首轮摸底发现等待和验证占了大部分时间时分析，不等整点检查点。多次短调用、重复构建和长日志的累计耗时也要考虑。

主 agent 读摘要和决定投入，执行者完成测量与深入诊断。先用已有证据做第一次判断，通常几分钟就够。

1. **定位耗时**：命令、输入规模、版本、预算和实测耗时；拆开排队、准备/构建、测试/评测、结果读取，指出哪一段拖住下一步。并行任务的耗时不能简单相加当作总等待时间。
2. **区分慢和卡住**：最近完成的单元、吞吐、预计剩余时间，以及 CPU/GPU、内存、I/O。持续输出不等于有效进展，低 CPU 也不能单独证明卡住。进度不可见时先取日志或补便宜的测量。
3. **做出决定**：必要且正常推进的继续；验证超出当前需要的调整范围并写明未覆盖什么；资源争用就错开；重复工作就复用结果；确定有收益的优化给出预算。取消或重跑前确认可恢复性和已有结果的保留方式。
4. **留下复查点**：任务 notes.md 记录“瓶颈 — 证据 — 决定 — 预计节省/剩余时间 — 下次复查时间或条件”。主 agent 在进度快照（当前目标目录的 PROGRESS.md）留责任人与下一步。继续等待也要约定下一次进度证据。

优先用摘要输出、复用有效结果、缓存、尽早失败、分片和资源允许的并行。用子集作代理评测前验证其代表性；不能删除关键断言、吞掉失败或减少必要覆盖来声称加速。

优化是否值得，按整个目标剩余工作中的收益和实现、验证成本判断；不确定时做最便宜的探测。在相同输入和环境下对比耗时，核对结果、失败检出与覆盖没有退化。没有实测收益就停止扩展这项优化。

脚本对同一次慢调用只提醒一次。复查条件由执行者主动回报、主 agent 的有界等待和下一次协调处理；当前没有通用的复查点定时器。主 agent 被权限请求或长工具调用阻塞时，不能保证 20 分钟内完成第一次判断。
