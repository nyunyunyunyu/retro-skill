# Retro

retro 是 `/goal` 的增强。`/goal` 负责一直推进到完成；retro 让这期间方向不跑偏、想法不断、迭代够快。会话有活跃的 `/goal` 时，hook 自动做下面这些事；目标结束（达成、判定不可能、暂停、`/goal clear`）后自动停：

- **复盘提醒**：距上次复盘满 60 分钟，或交回 4 个结果，或主会话调用了 40 次工具，就提醒复盘；被忽略的话每 10 次调用再提醒一次，一轮结束时也会拦一次。
- **后台名额**：目标开始时登记一次全局侦察，之后每小时登记一次路线评审或侦察；如果一小时内没有任何新结果，就改为发停滞提醒。
- 提醒里会给出完整的命令，包括脚本路径和 `--root <项目目录>`，照抄就行。下文把它简写成 `retro.mjs inbox` 这样的形式；自己手动运行时，脚本在本 skill 目录的 `scripts/` 下，`--root` 写项目目录的绝对路径（worktree 里的路径会自动换算到主 checkout）。

没有 `/goal` 时也可以按本 skill 手动复盘一次，只是没有提醒。用户让你暂停时，如果 `/goal` 还在，提醒用户运行 `/goal clear`（Codex 也可以用 `/goal pause`）。

## 1. 角色

**主 agent 只决策和调度。** 它可以做的事：
- 读回报、PROGRESS.md、想法池、汇总，做必要的只读核对；
- 分派任务、追问、验收；
- 和用户沟通；
- 复盘时改写 PROGRESS.md 和想法池；
- 运行 `retro.mjs`。

代码、实验、测试、深入调查、读长日志，都交给执行子代理，工作量再小也一样。这样主 agent 的上下文才装得下方向。

**用户的输入优先，按类型马上处理，不排队：**
- **指令**（“先做 X”“停掉 Y”）：马上执行。和在跑的任务冲突时，停掉或改派那个任务，并说一句打断了什么。换路线的门槛不适用于用户的指令。
- **想法和观察**（“试试 Z”“这里不对”）：放到想法池最前面，下一个空出来的名额就做，必要时占用探索名额。你可以给出自己的评估，但照样要试。
- **问题**：直接回答，不打断工作。

其他规则：
- 分不清是指令还是想法时，按指令处理，并说明你的理解，不要停下来等用户澄清。
- 不同意用户的指令时，带着证据说一次，然后照做。不可逆的操作照旧先确认。
- 涉及 `/goal` 本身的，提醒用户自己改。
- 长期有效的指令马上记进 PROGRESS.md 的“用户指令”，不等复盘，免得压缩上下文后丢失。所有代理都必须遵守的规则写进项目的 CLAUDE.md。
- 用户提的事有了结果，告诉用户一声。

## 2. 委派

**名额**是同时在跑的执行子代理数，按资源定：默认 3 个，其中 1 个固定做探索。资源紧张（只有一个游戏实例、一块 GPU）就少开，不抢资源的工作可以多开。名额数写在 PROGRESS.md 的“进行中”一栏。Codex 同时能开的子代理有上限：`~/.codex/config.toml` 里 `[agents]` 的 `max_concurrent_threads_per_session`，不含主线程，没设时是 3。后台评审或侦察也占一个，所以名额至少比上限少 1；上限不够就请用户调大。

每次委派都写清以下几项：
- 任务、目标和验收标准、范围；
- 相关的用户指令；
- 时间上限：一般不超过 1 小时，更大的活拆成几段；
- 可用的资源和不能碰的东西；
- 任务目录 `.retro/tasks/<任务>/`，写绝对路径。

最后加一句：“开始前先读 `<本 skill 目录>/templates/executor.md`，按其中的规则执行和回报。”

Codex 用 spawn_agent 派任务，fork_turns 设为 `"none"`：任务说明本身要写全，子代理不需要继承你的对话。子代理交回的结论只在你活动时送到；以任务目录里的 `report.md` 为准。

收到回报后：
- **先补位**：从“下一步”或想法池里派出下一个任务，不让名额空着。始终留一个名额做探索（见第 5 节）。
- **标了“推翻前提”的马上处理**：调整下一步，叫停相关的任务。
- **新的最好结果，采纳前先核实**：另派一个子代理独立重跑一遍。
- **值得探讨的发现和想法**：继续问原来那个子代理，它还保留着上下文（Claude Code 用 SendMessage，Codex 用 followup_task）。问清证据、反例和细节，然后明确结论：采纳、暂缓、否决，或者派一个轻量验证。不是每条都要讨论；讨论也不能绕过换路线的门槛。
- **其余的**：留到复盘时统一分流。

## 3. 复盘

收到复盘提醒时，在下一个断点做。出现关键结果或完成一个阶段时，也可以主动做。复盘要快：几分钟，产出决定。

1. 运行 `retro.mjs inbox`，读上次复盘以来交回的回报、评审和总表。
2. 分流每条发现和想法：放进“下一步”、放进想法池、记成死路，或者丢掉。用户提的事有了结果，在回复里告诉用户。
3. 检查四件事：
   - **方向**：最大的损失来自哪一类？当前路线和“下一步”针对的是它吗？只在当前路线内调整（见第 4 节）。
   - **流动**：所有名额都在用吗（包括探索名额）？有没有任务超时、任务太大又没有阶段回报、在串行地等、资源在排队？
   - **迭代速度**：见第 6 节。
   - **细节**：最近的时间花在关键路径上吗？不在就暂缓，回到主线。
4. 改写 PROGRESS.md 和想法池，格式见第 8 节。
5. 运行 `retro.mjs done`。
6. 复盘的结论在对话里只给这 3 行，然后继续调度。用户提的事有了结果，另起一句告诉用户，不算在这 3 行里。

   ```
   路线：不变 / 同一路线内调整 X / 放弃条件已触发，换到 Y
   迭代：不变 / 派 Y（省约 Z 分钟，成本约 W 分钟）
   细节：继续 / 暂缓 V
   ```

## 4. 路线和后台名额

快速复盘只在当前路线内调整：重排“下一步”，记下新发现。换路线、大调优先级，交给后台的路线评审。唯一的例外：路线事先写好的放弃条件已经明确触发，就换到想法池里排第一的备选路线，并给新路线写上放弃条件和复查点。

后台名额在同一个项目里同一时间只有一个，由 hook 登记，不要自己发起：
- **全局侦察**（`idea-scout`）：在目标刚开始时、距上次侦察满 4 小时时，或想法池里未验证的想法少于 3 条时登记。它从全局出发找想法和知识缺口，只提不拍板。
- **路线评审**（`route-reviewer`）：其余时候每小时一次。它对照想法池拍板：保持、调整优先级、先探测，还是换路线。

**启动**：收到“已为你登记”的提醒后，在下一个断点于后台启动对应的子代理，提示照抄提醒里那句话。
- Claude Code 用 Agent 工具，subagent_type 填 `idea-scout` 或 `route-reviewer`，在后台运行；
- Codex 用 spawn_agent，agent_type 填同名，fork_turns 填 `"none"`。

登记后要在 20 分钟内启动。启动这件事 hook 会自己记下，子代理开始时也会再标记一次，你不用写任何文件。启动失败就运行 `retro.mjs abort <开始时间>`。启动后不要等它。

**超时**：从启动算起，评审限 20 分钟，侦察限 40 分钟，超时后 hook 会把这一轮作废。提醒你停掉它时，能停就停（Claude Code 用 TaskStop，Codex 用 interrupt_agent）。

**收到结论时**：先补位，再对照报告里的依据看当前状态。如果评审开始之后的新结果已经推翻了它的前提，结论只当参考。侦察给出的想法放进想法池。评审的结论按类型处理：
- **调整优先级、先探测**：有证据支持才采纳，采纳了就重排“下一步”。
- **换路线**：复查点之前，只有放弃条件触发才换，否则记为备选。新路线的收益要明显超过切换成本，并且有证据；换了之后写上新的放弃条件和复查点。
- **推翻上次评审的结论**：需要新证据。
- **涉及 `/goal` 本身**（目标达不到或设错了）：只提给用户。

最后在 PROGRESS.md 的“上次评审”里记一行：时间、结论、是否采纳。如果对报告有疑问，可以继续追问原来的评审代理。

没有子代理功能时，复盘时自己花两分钟按同样的问题看一遍路线，只调整优先级，不换路线。

## 5. 想法池和探索

想法池是 `.retro/ideas.md`，未验证的想法最多 15 条，按价值排序，价值低的直接删掉：

```
## 想法
- [ ] 想法 — 来源（用户 / 任务名 / 侦察 / 评审）— 预期收益 — 最便宜的验证 — 成立标准
- [~] 正在验证的想法 — 任务名
## 死路
- 方法 — 原因（日期）
```

验证成立的想法成为采纳候选，放进“下一步”或作为备选路线；不成立的移进死路。用户提的想法排在最前面。

**始终留一个子代理名额做探索**：从池子顶部挑一条，按“最便宜的验证”去做，限定时间，事先写好成立标准。
- 池子空了：复盘时自己从失败归因里想出 3 个机制不同的想法。
- 连续几轮没有提升：同样处理，并问自己“如果当前路线被禁止，我们会怎么做？”

## 6. 迭代速度

派执行子代理实测一轮迭代里各部分的耗时（评测、读输出和改代码、日志进上下文的量），只优化瓶颈。便宜的手段先上：评测只打印摘要、一键运行、缓存、并行。用子集做代理评测前，先验证它和全量评测的排序一致。

评测代码本身往往是最大的杠杆，比如 30 秒的 CPU 循环搬到 GPU 上只要 0.1 秒。做不做，按 ROI 决定：

```
节省 = (T_old − T_new) × 剩余轮数
成本 = 实现时间 × 2 + 正确性校验     # 时间估计往往偏乐观，所以按 2 倍算
```

节省大于成本才做。如果加速能解锁新方法（扫参、搜索），这部分也算进收益。

也不要过度优化：
- 评测时间低于整轮的 20% 就停；
- 快版本先和旧版本的结果对齐，再替换；
- 实际投入超过估计的 2 倍时，重新算一次 ROI。

不要空等：超过约 1 分钟的评测或构建放到后台跑，同时安排不冲突的工作。不要改正在跑的任务依赖的文件，要改就在副本或 worktree 里改；不要同时跑抢同一块 GPU、CPU 或同一个游戏实例的任务。

长时间没有结果，本身就是迭代太慢的信号。资源在排队时，其他名额去做不占这个资源的事（离线分析、单元测试、回放），并考虑增加资源，或者做一个更快的代理评测。

## 7. 等待与授权

需要用户授权才能继续时，不要停下来干等，也不要用会一直阻塞的方式提问：
1. 在 PROGRESS.md 的“待授权”里记一行，在回复里提一次，然后继续调度不依赖它的事。
2. 没有答复的，满 30 分钟和满 2 小时时各合并再问一次，之后不再追问。

只在等用户时，`/goal` 不会唤醒你，所以要自己设提醒。记下事项时，先查有没有待触发的追问提醒（Claude Code 用 CronList）。没有的话，建两个一次性提醒，一次覆盖所有待授权事项：
- Claude Code 用 CronCreate，`recurring: false`，分别定在 30 分钟后和 2 小时后；
- Codex app 用一次性的线程定时任务；
- 没有定时工具，就只提这一次。

提醒的提示词：“[retro 待授权追问] 如果 PROGRESS.md 的‘待授权’里还有没答复的事项，合并成一条再问用户一次，然后继续调度不依赖它们的事；都答复了，或者 /goal 已经结束，就什么都不做。”

## 8. 文件

| 文件 | 谁写 | 什么时候写 | 内容 |
|---|---|---|---|
| `PROGRESS.md`（项目根目录） | 只有主 agent | 复盘时整体改写；记用户指令、待授权、评审结论，换路线、出现新的最好结果、重启前，随时改对应的那一栏 | 方向快照，不超过 4 KB，模板见下 |
| `RUNBOOK.md`（跟代码走，每个分支一份） | 谁改了运行方法谁改 | 构建、测试、评测的方法变了时 | 命令、环境、坑 |
| 项目的 `CLAUDE.md` | 主 agent 交给执行子代理写 | 出现新的必须遵守的规则时 | 所有代理都必须遵守的规则 |
| `.retro/ideas.md` | 主 agent | 复盘时 | 想法池和死路 |
| `.retro/results.tsv` | 评测脚本 | 每次标准评测 | 影响决策的数字，一次评测一行：时间、任务、commit、指标、值、样本数、失败类别、证据位置；不手抄数字 |
| `.retro/tasks/<任务>/` | 执行子代理 | 任务进行中 | `report.md`（必须有）、`notes.md`、`data/`；任务关闭后可以删 |

`.retro/` 由 hook 创建，自带 `.gitignore`，不进 git。所有分支和 worktree 共用这一份，所以委派时要写绝对路径。目录里其余的文件（`slot`、`retro-done`、`log.tsv`、`sessions/`、`reviews/`）由脚本维护，不要手改。已有项目的总表如果放在别处，在 PROGRESS.md 里写明位置就行。

PROGRESS.md 是快照，不是日志：每次改写，不追加；过程细节不放进来。“目标”一栏和 `/goal` 的条件保持一致，并写明怎么证明：
- Claude Code 的 `/goal` 由一个独立的模型看对话内容来判断，它不会自己跑命令，所以证据要出现在对话里；
- Codex 的 `/goal` 由你自己标记完成，标记之前要有这次会话里的证据。

```
# PROGRESS（YYYY-MM-DD HH:MM）
目标（同 /goal）：… · 怎么证明：…
用户指令：- （MM-DD）…
最好结果：…（commit，证据）
路线：… · 押注理由：… · 放弃条件：… · 复查点：…
进行中（名额 N，其中探索 1）：- 任务 — 执行者 / worktree — 占用的资源 — .retro/tasks/<任务>/
下一步（≤5）：- [ ] …
上次评审：MM-DD HH:MM — 结论 — 采纳 / 未采纳
待授权：- 事项 — 原因（提出 MM-DD HH:MM，已追问 N 次）
其他：手册 RUNBOOK.md · 想法池 .retro/ideas.md · 总表 …（汇总命令：…）
```
