# Retro

retro 是 `/goal` 的增强。`/goal` 负责一直干到完成：每轮结束后判断条件是否达成，没达成就自动继续，达成后自动结束。retro 补上 `/goal` 没有的定期复盘：会话有活跃的 `/goal` 时，提醒 hook 每 40 次工具调用提醒一次快速复盘，每小时提醒一次在后台启动路线评审；目标结束（达成、判定不可能、`/goal clear`；Codex 是完成或 `/goal pause`）后自动停。没有 `/goal` 时也可以手动调用 retro 复盘一次，只是不会有自动提醒。

复盘要快：几分钟，产出决定，不写文章。最近刚做过就跳过。

用户让你暂停时，如果 `/goal` 还在，提醒用户运行 `/goal clear`（Codex：`/goal pause`）。你自己停不下 `/goal`，它会让你接着干。

## 1. 路线

快速复盘里只在当前路线内做小调整：重排“下一步”，记下新发现。要不要换路线、优先级要不要大调，交给后台的路线评审（见下一节），不要在快速复盘里直接换路线，也不要自己提前发起评审。唯一的例外：当前路线事先写好的放弃条件已经明确触发，就按规则换到“备选”里的路线，并写上新的放弃条件和复查点。这是预先承诺的规则，不算临时换路线。其他强信号（关键假设被证伪、几轮都没有提升、修一个坏一个）记进 PROGRESS.md，下次评审会看到。

## 路线评审

在后台跑，不阻塞你。同一项目同一时间最多一个，状态记在 `.retro/route-review.md` 的第一行。何时评审由 hook 决定：目标开始满 1 小时后、以及每次评审开始满 1 小时后，hook 会原子地登记一次（把第一行写成 `running`）再提醒你。不要自己登记，也不要自己提前启动。

- **启动**：收到“已为你登记”的提醒后，在下一个自然断点于后台启动 route-reviewer：Claude Code 用 Agent 工具，subagent_type 填 `route-reviewer`；Codex 用 route-reviewer 子代理。提示照抄提醒里那句，带上开始时间。启动后马上在第一行的 `-->` 前面加上 ` spawned=<当前 UTC 时间，ISO 格式>`，其余原样保留，hook 看到 spawned 就不再催。启动失败就把 `running` 改成 `aborted`。不要等它，接着干活。只有登记它的会话会收到这些提醒，别的会话不用管。
- **超时**：超过 20 分钟，hook 会自动把这轮改成 `aborted`，结论作废。如果提醒你停掉它，能停就停（Claude Code 用 TaskStop，Codex 用 close_agent）；停不掉也没关系，它交结论前会发现已作废，不会写入。
- **收到结论**：先做完手头这一步，再对照报告里的“依据”看当前状态。评审开始后出现的新结果已经推翻了它的前提，就只当参考。然后：
  - 调整优先级、先探测：有新证据支持才采纳，采纳了就重排“下一步”。
  - 换路线：复查点之前，只有放弃条件触发才换，否则记进“备选”。新路线的收益要明显超过切换成本，并且有证据。换了之后，给新路线写上新的放弃条件和复查点。
  - 推翻上次评审的结论需要新证据。
  - 涉及 /goal 本身（条件达不到或设错了）：只提给用户，不自己改目标。
  - 在 PROGRESS.md 的“上次评审”一栏记一行：时间、结论、是否采纳。
- **没有子代理功能时**：复盘时自己花两分钟按同样的问题看一遍路线，只调整优先级，不换路线。

`.retro/` 不需要提交，可以加进 `.gitignore`。

## 2. 迭代速度

先实测一轮里各部分的耗时（评测、读输出和改代码、日志进上下文的量），只优化瓶颈。便宜的手段先上：评测只打印摘要、一键化、缓存、并行；用子集做代理评测时，先验证它和全量评测的排序一致。

不要空等评测。超过约 1 分钟的评测放到后台跑（Claude Code 用 run_in_background，其他工具用后台进程），等待期间为下一步做准备：读代码、准备下一个改动、分析已有结果，或者用 subagent / worktree 试另一条路线。几点注意：不要改正在跑的评测所依赖的文件，要改就在副本或 worktree 里改；不要同时跑抢同一 GPU/CPU 的任务，否则计时会失真，显存不够时评测还可能直接崩掉；结果一出来就回到主线。

评测代码本身往往是最大的杠杆，比如 30s 的 CPU 循环搬到 GPU 后只要 0.1s。不要因为它“不是主线”就跳过，按 ROI 决定：

```
节省 = (T_old − T_new) × 剩余轮数
成本 = 实现时间 × 2 + 正确性校验     # 估计偏乐观，按 2 倍计
```

节省大于成本才做。如果加速能解锁新方法（扫参、搜索），把这部分也算进收益。

不要过度优化：评测低于整轮的 20% 就停；快版本先在参考集上和旧版本对齐再替换；实际投入超过估计 2 倍时重新算 ROI；不做通用框架。

## 3. 细节与等待

最近的时间花在关键路径上吗？不在就记入“暂缓”，回主线。在关键路径上但反复失败，就换个角度（最小复现、二分、读源码），或者先绕开。

需要用户授权才能继续的事，不要停下来干等，也不要用会一直阻塞的提问方式。在 PROGRESS.md 的“待授权”里记一行，在回复里提一次，然后继续做不依赖它的事。没有答复的，满 30 分钟和满 2 小时时各合并再请求一次，之后不再追问。你只等用户时，`/goal` 不会唤醒你，所以记下事项时，如果还没有待触发的追问提醒（Claude Code 用 CronList 查看），就建两个一次性提醒，一次覆盖所有待授权事项：Claude Code 用 CronCreate，`recurring: false`，分别定在 30 分钟后和 2 小时后；Codex app 用一次性的线程定时任务；没有定时工具就只提这一次。提醒的提示词用：“[retro 待授权追问] 如果 PROGRESS.md 的“待授权”里还有没答复的事项，合并成一条再问用户一次，然后继续做不依赖它们的事；都答复了，或者 /goal 已经结束，就什么都不做。”只剩等待项的时候，从“下一步”或“暂缓”里挑不依赖它们的事做；真没有就说明在等什么，结束这一轮。

## 4. PROGRESS.md

放在项目根目录。它是快照，不是日志：每次复盘都改写它（至少更新日期），而不是追加，不超过约 60 行。提醒 hook 靠它的修改时间判断复盘做了没有。实验数字追加到 `results.tsv`，改动原因写进 commit message，已完成的细节直接删掉。死路每条一行，防止重复尝试。目标结束后它留作记录，下一个目标开始时改写它。

“目标”一栏和 `/goal` 的条件保持一致。条件要可验证，并写明怎么证明（例如“`npm test` 退出码为 0”）：Claude Code 的 `/goal` 由一个独立的模型看对话内容来判断，它不会自己去跑命令。Codex 的 `/goal` 由你自己标记完成，标记之前要有这次会话里的证据。

```
# PROGRESS（YYYY-MM-DD）
目标（同 /goal）：… · 怎么证明：…
最好结果：…（commit）
路线：… · 押注理由：… · 放弃条件：… · 复查点：…（最多几轮实验或到什么时候）
迭代：`命令` · T_eval ≈ …s
下一步（≤5）：- [ ] …
备选：- 路线 — 什么情况下值得换
上次评审：MM-DD HH:MM — 结论 — 采纳 / 未采纳
死路：- 方法 — 原因
暂缓：- …
待授权：- 事项 — 原因（提出 MM-DD HH:MM，已追问 N 次）
```

## 5. 输出

在对话里只给这 3 行，每行一句，不另写总结，然后继续干活：

```
路线：不变 / 同一路线内调整 X / 放弃条件已触发，换到备选 Y
迭代：不变 / 做 Y（省约 Z 分钟，成本约 W 分钟）
细节：继续 / 跳过 V（已记入暂缓）
```
