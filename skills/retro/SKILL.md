# Retro

复盘要快：几分钟，产出决定，不写文章。最近刚做过就跳过。

## 1. 路线

信号：几轮没有提升、修一个坏一个、改动越来越像打补丁。有信号时，列 2–3 条本质不同的路线，用最便宜的实验验证最有希望的一条。重大决策可以交给一个全新的 subagent，只给它目标和 PROGRESS.md，让它独立评估，避开沉没成本。

## 2. 迭代速度

先实测一轮里各部分的耗时（评测、读输出和改代码、日志进上下文的量），只优化瓶颈。便宜的手段先上：评测只打印摘要、一键化、缓存、并行；用子集做代理评测时，先验证它和全量评测的排序一致。

不要空等评测。超过约 1 分钟的评测放到后台跑（Claude Code 用 run_in_background，其他工具用后台进程），等待期间为下一步做准备：读代码、准备下一个改动、分析已有结果，或者用 subagent / worktree 试另一条路线。几点注意：不要改正在跑的评测所依赖的文件，要改就在副本或 worktree 里改；不要同时跑抢同一 GPU/CPU 的任务，否则计时会失真，显存不够时评测还可能直接崩掉；结果一出来就回到主线。

评测代码本身往往是最大的杠杆，比如 30s 的 CPU 循环搬到 GPU 后只要 0.1s。不要因为它“不是主线”就跳过，按 ROI 决定：

```
节省 = (T_old − T_new) × 剩余轮数
成本 = 实现时间 × 2 + 正确性校验     # 估计偏乐观，按 2 倍计
```

节省大于成本才做。如果加速能解锁新方法（扫参、搜索），把这部分也算进收益。

不要过度优化：评测低于整轮的 20% 就停；快版本先在参考集上和旧版本对齐再替换；实际投入超过估计 2 倍时重新算 ROI；不做通用框架。

## 3. 细节

最近的时间花在关键路径上吗？不在就记入“暂缓”，回主线。在关键路径上但反复失败，就换个角度（最小复现、二分、读源码），或者先绕开。

## 4. PROGRESS.md

放在项目根目录，它的存在也会开启复盘提醒 hook。它是快照，不是日志：每次复盘都改写它（至少更新日期），而不是追加，不超过约 60 行。提醒 hook 靠它的修改时间判断复盘做了没有。实验数字追加到 `results.tsv`，改动原因写进 commit message，已完成的细节直接删掉。死路每条一行，防止重复尝试。任务完成后删掉 PROGRESS.md，提醒随之关闭。

```
# PROGRESS（YYYY-MM-DD）
目标：… · 完成标准：…
最好结果：…（commit）
路线：…
迭代：`命令` · T_eval ≈ …s
下一步（≤5）：- [ ] …
死路：- 方法 — 原因
暂缓：- …
```

## 5. 输出

在对话里只给这 3 行，每行一句，不另写总结，然后继续干活：

```
路线：不变 / 改为 X（验证实验：…）
迭代：不变 / 做 Y（省约 Z 分钟，成本约 W 分钟）
细节：继续 / 跳过 V（已记入暂缓）
```
