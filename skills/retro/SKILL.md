# Retro

复盘要快：几分钟，产出决定，不写文章。最近刚做过就跳过。

## 命令

只有用户明确输入这些命令时才执行（Claude Code：`/retro pause`；Codex：`$retro pause`）；唯一的例外是你按第 4 节确认任务完成后自己执行 `done`。除了 `resume`，执行时都不复盘，做完用一句话确认：

- `pause`：把 PROGRESS.md 改名为 `PROGRESS.paused.md`（这个文件已存在就先问用户），删掉本会话的定时检查。整个项目的提醒立刻停止，其他会话的定时检查会在下次触发时删掉自己。
- `resume`：有 `PROGRESS.paused.md` 就恢复它；没有的话找最新的 `PROGRESS.done-*.md`，把它的日期和“目标”那一行给用户看，确认后再恢复（撤销 done）；都没有就说明情况，什么都不做。PROGRESS.md 已经存在就先问用户留哪个。恢复后复盘一次，然后接着干活。复盘会改写 PROGRESS.md；只改名不会刷新修改时间，提醒会马上判定逾期。
- `done`：把 PROGRESS.md 改名为 `PROGRESS.done-YYYYMMDD-HHMM.md` 留作记录，删掉本会话的定时检查。

用户用自己的话让你暂停或停下，只是暂停这个会话：删掉本会话的定时检查，停下来，等用户说继续再重建。不动 PROGRESS.md。

不管哪种暂停，本会话有活跃的 `/goal` 时，都要提醒用户运行 `/goal clear`（Codex：`/goal pause`）。你自己清除不了目标，不清的话 `/goal` 会让你接着干。

## 定时检查

长任务里要有一个每 10 分钟的定时检查。在等待或等授权时不调用工具，靠工具调用触发的提醒就失效了。会话被用户暂停期间不要建。先查有没有（Claude Code 用 CronList），没有才建：Claude Code 用 CronCreate，cron 填 `*/10 * * * *`；Codex app 用线程定时任务。它只在会话空闲时触发。提示词用：

```
[retro 定时检查] 如果自上次定时检查以来用户打断过你或让你暂停、而且还没说继续，或者 PROGRESS.md 已不存在，就删掉这个定时任务，然后结束。如果按 retro skill 第 4 节确认任务已经完成，就执行 done，然后结束。否则：① 在等的后台任务有结果了就处理；② “待授权”里没答复的事项，提出满 30 分钟时合并再问一次，满 2 小时时最后问一次，之后不再追问；③ 只能等的话，从 PROGRESS.md 的“下一步”或“暂缓”里挑不依赖等待项的事做；没有就用一句话说明在等什么，然后结束。
```

## 1. 路线

信号：几轮没有提升、修一个坏一个、改动越来越像打补丁。有信号时，列 2–3 条本质不同的路线，用最便宜的实验验证最有希望的一条。重大决策可以交给一个全新的 subagent，只给它目标和 PROGRESS.md，让它独立评估，避开沉没成本。

## 2. 迭代速度

先实测一轮里各部分的耗时（评测、读输出和改代码、日志进上下文的量），只优化瓶颈。便宜的手段先上：评测只打印摘要、一键化、缓存、并行；用子集做代理评测时，先验证它和全量评测的排序一致。

不要空等评测。超过约 1 分钟的评测放到后台跑（Claude Code 用 run_in_background，其他工具用后台进程），等待期间为下一步做准备：读代码、准备下一个改动、分析已有结果，或者用 subagent / worktree 试另一条路线。几点注意：不要改正在跑的评测所依赖的文件，要改就在副本或 worktree 里改；不要同时跑抢同一 GPU/CPU 的任务，否则计时会失真，显存不够时评测还可能直接崩掉；结果一出来就回到主线。

评测代码本身往往是最大的杠杆，比如 30s 的 CPU 循环搬到 GPU 后只要 0.1s。不要因为它“不是主线”就跳过，按 ROI 决定：

```
节省 = (T_old − T_new) × 剩余轮数
成本 = 实现时间 × 2 + 正确性校验     # 估计偏乐观，按 2 倍计
```

节省大于成本才做。如果加速能解锁新方法（扫参、搜索），把这部分也算进收益。

不要过度优化：评测低于整轮的 20% 就停；快版本先在参考集上和旧版本对齐再替换；实际投入超过估计 2 倍时重新算 ROI；不做通用框架。

## 3. 细节与等待

最近的时间花在关键路径上吗？不在就记入“暂缓”，回主线。在关键路径上但反复失败，就换个角度（最小复现、二分、读源码），或者先绕开。

需要用户授权才能继续的事，不要停下来干等，也不要用会一直阻塞的提问方式。在 PROGRESS.md 的“待授权”里记一行，在回复里提一次，然后继续做不依赖它的事。没有答复的事项由定时检查追问，最多再问两次。

## 4. PROGRESS.md

放在项目根目录，它的存在会开启复盘提醒 hook。它是快照，不是日志：每次复盘都改写它（至少更新日期），而不是追加，不超过约 60 行。提醒 hook 靠它的修改时间判断复盘做了没有。实验数字追加到 `results.tsv`，改动原因写进 commit message，已完成的细节直接删掉。死路每条一行，防止重复尝试。

完成标准要可验证（测试通过、指标达到多少、命令输出什么），最好原样写进 `/goal`：Claude Code 的 `/goal` 每轮由一个独立的模型判断是否达成，没达成会自动继续干。确认完成的条件：Claude Code 的 `/goal` 已判定达成，或者完成标准逐条都有这次会话里的证据（命令输出、测试或评测结果）。Codex 的 `/goal` 是你自己标记完成的，不算独立判定，要有证据。确认后自己执行 `done`，告诉用户已归档，误判了可以用 `/retro resume`（Codex：`$retro resume`）撤销。拿不准就不执行，接着干或者问用户。

```
# PROGRESS（YYYY-MM-DD）
目标：… · 完成标准：…
最好结果：…（commit）
路线：…
迭代：`命令` · T_eval ≈ …s
下一步（≤5）：- [ ] …
死路：- 方法 — 原因
暂缓：- …
待授权：- 事项 — 原因（提出 MM-DD HH:MM，已追问 N 次）
```

## 5. 输出

在对话里只给这 3 行，每行一句，不另写总结，然后继续干活：

```
路线：不变 / 改为 X（验证实验：…）
迭代：不变 / 做 Y（省约 Z 分钟，成本约 W 分钟）
细节：继续 / 跳过 V（已记入暂缓）
```
