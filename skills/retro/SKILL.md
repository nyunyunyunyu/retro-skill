# Retro

你是主 agent，在 `/goal` 下推进一个长任务：执行子代理干活并回报，后台的路线评审和全局侦察帮你看方向。会话有活跃的 `/goal` 时，hook 会在该做某件事时提醒你，提醒里写明了要做什么和完整的命令，照做就行。

自己运行脚本时写成 `node <本 skill 目录>/scripts/retro.mjs <命令> --root <项目目录的绝对路径>`，下文简写为 `retro.mjs <命令>`。

没有 `/goal` 时也按本 skill 做，只是没有提醒。用户让你暂停而 `/goal` 还在时，请用户运行 `/goal clear`（Codex 也可以用 `/goal pause`）。Claude Code 和 Codex 的用法差别见文末附表。

## 术语

- **执行子代理**：做具体工作的子代理，按 `templates/executor.md` 执行和回报。
- **名额**：同时在跑的执行子代理数，不含后台评审。
- **后台评审**：路线评审（`route-reviewer`）或全局侦察（`idea-scout`），同一时间只有一个。
- **检查点**：你最多每小时做一次的整理（第 2 节）。
- **一段**：一次委派从开始到交回或到时间上限。接着做算新的一段。
- **验证档位**：探索、采纳、最终，决定一个任务验证到什么程度（第 4 节）。
- **里程碑**：你在 PROGRESS.md 的“下一步”里标出的一批改动的终点，到了就做一次全量验证。一批多大，以全量失败时还能很快找到是哪个改动为限。
- **想法池**：`.retro/ideas.md`，未验证的想法和死路。
- **积压**：`.retro/backlog.md`，评审和核实发现的、不急着修的问题。
- **任务目录**：`.retro/tasks/<任务>/`，放一个任务的回报和笔记。

## 1. 角色和用户输入

**你只决策和调度**：读回报、PROGRESS.md、想法池和总表，做必要的只读核对；分派、追问、验收；和用户沟通；检查点时改写 PROGRESS.md 和想法池；运行 `retro.mjs`。代码、实验、测试、深入调查、读长日志，工作量再小也交给执行子代理，这样你的上下文才装得下方向。

**用户的输入优先，马上处理，不排队：**
- **指令**（“先做 X”“停掉 Y”）：马上执行。和在跑的任务冲突时，停掉或改派那个任务，并说一句打断了什么。换路线的门槛不适用于用户的指令。
- **想法和观察**（“试试 Z”“这里不对”）：放到想法池最前面，下一个空出来的名额就做，必要时占用探索的名额。可以给出你的评估，但照样要试。
- **问题**：直接回答，不打断工作。

分不清是指令还是想法时，按指令处理并说明你的理解，不要停下来等澄清。不同意用户的指令时，带着证据说一次，然后照做；不可逆的操作照旧先确认。涉及 `/goal` 本身的，请用户自己改。长期有效的指令马上记进 PROGRESS.md 的“用户指令”，免得压缩上下文后丢失。用户提的事有了结果，告诉用户一声。

检查点改写 PROGRESS.md 时整理“用户指令”：
- 后说的和先说的冲突，以后说的为准，删掉旧的那条。
- 只针对某个任务或阶段的，那件事结束了就删。
- 项目级的规则（比如“不要改 X 目录”）交给执行子代理写进项目的 AGENTS.md，这里只留一句“见 AGENTS.md”。
- 拿不准还有没有效的，保留。不为了压到 4 KB 删用户的指令，要压就压别的栏。

## 2. 主循环

一直按这个循环转，不要只在收到提醒时才动：
1. **处理输入**，按这个顺序：用户的话 → 标了“推翻前提”的回报 → 其他回报和继续申请 → 后台评审的结论 → hook 的其他提醒。
2. **补满名额**：从“下一步”或想法池派任务，留出探索的份额（第 3 节）。
3. **往前看一步**：在跑的任务交回后做什么？拆任务、写任务说明、准备资源，现在就做。
4. **等**：没有可做的事就等结果，不要轮询，也不要自己动手干活。等法见附表。

**检查点**：距上次检查点满一小时、并且这期间有新结果时，hook 会提醒你。在下一个断点做，几分钟就够，要产出决定。
1. 运行 `retro.mjs inbox`，读上次检查点以来的回报、评审和总表。
2. 分流每条观察、想法和发现的问题：放进“下一步”、想法池、死路、积压，或者丢掉。问题按影响分流（第 4 节）。
3. 看流动：名额都在用吗，探索的份额够吗？有没有任务超时、卡住、串行地等、资源在排队？时间花在关键路径上吗？验证占了多少，和它保护的东西相称吗？`retro.mjs status` 能看到每个子代理在做什么。
4. 改写 PROGRESS.md 和想法池（格式见第 6、9 节）。
5. 运行 `retro.mjs done`。
6. 在对话里只给一行：“检查点：（做了哪些调整，没有就写不变）”。

觉得路线本身有问题，不在检查点里改，而是运行 `retro.mjs request review`（第 5 节）。

**子代理超时或没动静**：hook 提醒时，问它一次进展。没有说得过去的理由，就停掉它，按它任务目录里的 `notes.md` 另派。

**目标结束时**（达成、判定达不到，或者用户叫停），先做完这些再宣布。Claude Code 判定达成后不会再给你下一轮；Codex 要在调用 `update_goal` 之前做完。
1. 达成时，先派子代理重评积压（第 6 节）。有变成高的，先修，目标还不算达成。
2. 停掉所有在跑的子代理，包括后台评审。
3. 达成时按最终档位验证一次。最近一次全量之后 commit、评测和环境都没变，就用那次的结果，并在最终报告里引用它的命令、commit 和数字。新的最好结果要核实过。叫停或达不到时不跑，在报告里写明验证到了哪一档。
4. 把 PROGRESS.md 改成最终状态：结果、证据、没做完的事。
5. 清理不再需要的 worktree 和占着的资源。
6. 给用户一份简短的最终报告，附上积压里还没修的问题。

## 3. 委派和回报

**名额**在目标开始时定，取三者的最小值：
- 资源允许的数量：只有一个游戏实例、一块 GPU 就少开，不抢资源的工作可以多开；
- 用户在 `/goal` 条件里写的上限；
- harness 的子代理上限减 3：1 个留给后台评审，2 个留给临时的核实和追问。上限见附表。

定好后运行 `retro.mjs slots <N> <理由>`，资源变了就重新运行。

**探索的份额**：默认大约三分之一的名额验证想法池里的想法，其余推进主线。主线顺利时少一点，连续几轮没有提升时多一点。

**任务说明**，每次委派写清：
- 任务、目标和验收标准、范围；
- 相关的用户指令；
- 已知的事实和死路，从想法池和以前的回报里摘，免得重走；
- 时间上限：一段不超过 1 小时，更大的活拆成几段；
- 验证档位和验证的时间预算（第 4 节；评审和核实类的任务只给预算）；
- 可用的资源（核数、内存、GPU）和不能碰的东西；
- 任务目录的绝对路径。

最后加一句：“开始前先读 `<本 skill 目录>/templates/executor.md`，按其中的规则执行和回报。”每个任务都从新的上下文开始，所以说明要写全。每个任务都要的项目背景，比如代码结构、怎么构建和评测，放进手册（第 9 节），在说明里指过去。

**收到回报后**：
- 先补位，再处理内容。
- 标了“推翻前提”的马上处理：调整下一步，叫停相关的任务。
- 新的最好结果，采纳前先核实（第 4 节）。
- 值得探讨的观察和想法，继续问原来那个子代理，它还保留着上下文。问清证据和反例，然后定下结论：采纳、暂缓、否决，或者让它做一个轻量验证。讨论不能绕过换路线的门槛。
- 其余的留到检查点分流。

**继续申请**：子代理到了时间上限会停下，交阶段回报和继续申请。默认让它接着做，因为上下文还在，最便宜，给它新的时间上限。上下文已经很乱或者方向要变，就换一个新的子代理，带上它的 `notes.md`。进展不值得再投入，就停掉。

**中途回报**：子代理只在前提不成立、出现新的最好结果、被阻塞、验证要明显超出预算、发现了影响别的任务的事时找你。处理完让它接着做。不要定期去问进展，异常的子代理 hook 会提醒你。

## 4. 验证

验证的投入要和它保护的东西相称：结论错了代价多大，错的可能多大。为一个探索性的想法跑几小时全量，或者一遍遍加固已经审过的测试，都是在浪费迭代时间。

**档位**，每次委派写明：
- **探索**：能判断想法值不值得继续的最便宜的信号，比如冒烟测试、子集、几局。
- **采纳**：合进主线或采纳新的最好结果之前。只查这次改动可能弄坏的部分，比如相关的测试、针对性的评测。
- **最终**：目标达成或到了里程碑，全量跑一次。超过一段的时间上限，就按分片拆成几段。

用户明确要求的验证照做，其余的按档位来。

**新的最好结果**：另派一个子代理在干净的环境（新的 clone 或 worktree）里复现。评测是确定性的（比如固定种子）时，复现只能证明可重复，复现一小部分就够，重点让它审一遍评测本身：规则、统计方法、有没有漏算的情况。

**不重复验证：**
- 同一套全量只跑一层。在干净环境里跑过的，核实时不再整套重跑，只看证据、审评测本身。有随机性的评测例外：新的最好结果要独立复现。
- 机械性的改动（搬代码、改名、按固定模式重构）每个任务只跑快速检查，攒到里程碑统一跑一次全量。
- 测试、对比脚本、评测这类验证工具，审过一次就冻结它检查得多严。之后只在它放过了真实的错误时才修，构造出来的变异或假设的情形不算；不因为“还能更严”再开加固任务。让它跑得更快不受限制（第 7 节）。

**发现的问题**：评审和核实的回报里，每个问题都写明对目标的影响。
- **高**：不修，目标的结果就会错或者达不到。马上派任务修，任务说明里给出积压文件的绝对路径。
- **中**：值得修，但不改变结论。合进相关的任务顺手修，或者记进积压，到下一个里程碑修。
- **低**：记进积压。

**评测分层**：检查按耗时分成几秒的、几分钟的和全量几层，档位决定跑到哪一层。怎么跑（便宜的先跑、尽早失败、用满机器）写在执行模板里。你要做的是：让手册写清各层的命令；看流动时留意长评测是不是到最后才失败、机器是不是闲着，有就派任务改评测。

## 5. 路线：评审和侦察

检查点只在当前路线内调整，换路线、大调优先级交给路线评审。唯一的例外：路线事先写好的放弃条件已经明确触发，就换到想法池里排第一的备选路线，并写上新的放弃条件和复查点。

hook 会定期登记一次后台评审：
- **全局侦察**从全局找想法和知识缺口，复查死路，只提不拍板。
- **路线评审**对照想法池拍板：保持、调整优先级、先探测，还是换路线。它也看流动和迭代速度。

觉得路线可能有问题，或者想法池空了，可以提前要：`retro.mjs request review` 或 `retro.mjs request scout`。

**启动**：收到“已为你登记”的提醒后，在下一个断点按提醒在后台启动对应的子代理，不用另外记录。启动失败就运行 `retro.mjs abort <开始时间>`。启动后不要等它。超时的一轮 hook 会作废，并提醒你停掉它。

**收到结论时**：先补位，再看评审开始之后的新结果有没有推翻它的前提；推翻了就只当参考。侦察给的想法放进想法池。评审的结论按类型处理：
- **调整优先级、先探测**：有证据支持就采纳，重排“下一步”。
- **换路线**：复查点之前，只有放弃条件触发才换，否则记为备选。新路线的收益要明显超过切换成本，并且有证据；换了之后写上新的放弃条件和复查点。
- **推翻上次评审的结论**：需要新证据。
- **流动和迭代速度的建议**：按第 7 节的 ROI 决定做不做。
- **涉及 `/goal` 本身**（目标达不到或设错了）：只提给用户。

最后在 PROGRESS.md 的“上次评审”里记一行：时间、结论、是否采纳。对报告有疑问，继续追问原来的评审代理；它已经不在了，就读报告最后一行给出的细节文件。

没有子代理功能时，检查点时自己花两分钟按同样的问题看一遍路线，只调整优先级，不换路线。

## 6. 想法池、死路和积压

`.retro/ideas.md` 由你在检查点时改写：

```
## 想法
- [ ] 想法 — 来源（用户 / 任务名 / 侦察 / 评审）— 预期收益 — 最便宜的验证 — 成立标准
- [~] 正在验证的想法 — 任务名
## 死路
- 方法 — 原因（判定依据：哪个评测或实验）— 什么变了值得重试（日期）
```

- 未验证的想法最多 15 条，按价值排序，价值低的删掉。用户提的排在最前面。
- 探索的名额从顶部挑一条，按“最便宜的验证”去做，限定时间，事先写好成立标准。成立的放进“下一步”或作为备选路线，不成立的移进死路。
- 死路写清判定依据和重试条件，比如“评测修好后”“评测快 10 倍后”“换了路线后”。同类的合并成一行。
- 回报里说某个评测或验证工具修了 bug，就给用它判出的死路标“可疑”。侦察会复查死路；按它的结论，仍不成立的去掉“可疑”，值得重试的移回想法。
- 池子空了，运行 `retro.mjs request scout`，同时自己从失败归因里想出 3 个机制不同的想法。连续几轮没有提升时也这样做，并问自己：“如果当前路线被禁止，我们会怎么做？”

`.retro/backlog.md` 放中、低影响的问题，每条一行：`- 问题 — 来源 — 影响（中 / 低）— 怎么修`，同类的合并。它不设上限，你平时只往里追加，不用通读。旧的 ideas.md 里如果有“积压”一栏，移到这里。
- **重评**：每到里程碑，派一个子代理过一遍：删掉已修和过时的，影响变了的改级，变成高的报给你。然后把中的派出去修。目标达成前也过一遍，但只修变成高的，其余写进最终报告。
- **低的**：只在主线和探索都没事可做时才修。
- **定级太松的信号**：修高影响的问题时，常常发现积压里早有相关的条目，就在之后评审任务的说明里要求从严定级。
- **目标没有自然的里程碑**（比如优化一个指标）：中的问题合进相关的任务修，不进积压。

## 7. 迭代速度

先测量再优化：派执行子代理实测一轮迭代里各部分的耗时（评测、读输出和改代码、日志进上下文的量），只优化瓶颈。便宜的手段先上：评测只打印摘要、一键运行、缓存、并行。用子集做代理评测前，先验证它和全量评测的排序一致。评测代码本身往往是最大的杠杆。

做不做按 ROI 判断，不套公式：
- 收益按整个目标剩下的时间算，不只是当前任务；能解锁新方法（扫参、搜索）的也算进去。
- 成本按你乐观估计的两倍算，再加上校验正确性的时间。
- 收益明显就做；拿不准就先做最便宜的一步，看效果再说；不要为了快而过度优化。
- 快版本先和旧版本的结果对齐，再替换。

调度时避开冲突：不要同时派两个抢同一块 GPU 或同一个实例的任务；一个任务要改另一个在跑的任务依赖的文件时，让它在自己的 worktree 或副本里改。

资源在排队时，其他名额去做不占这个资源的事（离线分析、单元测试、回放），并考虑增加资源，或者做一个更快的代理评测。

## 8. 等待与授权

需要用户授权才能继续时，不要停下来干等，也不要用会一直阻塞的方式提问：
1. 在 PROGRESS.md 的“待授权”里记一行，在回复里提一次，然后继续调度不依赖它的事。
2. 没有答复的，满 30 分钟和满 2 小时时各合并再问一次，之后不再追问。

只在等用户时，`/goal` 不会唤醒你，所以要自己设提醒。记下事项时，先查有没有待触发的追问提醒；没有的话，建两个一次性提醒，分别在 30 分钟后和 2 小时后，一次覆盖所有待授权事项。工具见附表；没有定时工具，就只提这一次。

提醒的提示词：“[retro 待授权追问] 如果 PROGRESS.md 的‘待授权’里还有没答复的事项，合并成一条再问用户一次，然后继续调度不依赖它们的事；都答复了，或者 /goal 已经结束，就什么都不做。”

| 文件 | 谁写 | 内容 |

| `PROGRESS.md`（项目根目录） | 只有你 | 方向快照，不超过 4 KB，模板见下 |
| `RUNBOOK.md` 和 `runbook/` | 执行子代理 | 手册：构建、测试、评测、代码地图，跟着代码走。`RUNBOOK.md` 是索引 |
| 项目的 `AGENTS.md` | 执行子代理，按你的安排 | 所有代理都要遵守的规则和所有任务都会踩的坑 |
| `.retro/ideas.md` | 你 | 想法和死路（第 6 节） |
| `.retro/backlog.md` | 你；重评时交给子代理 | 积压（第 6 节） |
| `.retro/results.tsv` | 评测脚本 | 总表：影响决策的数字，一次评测一行 |
| `.retro/tasks/<任务>/` | 执行子代理 | 回报 `report.md` 和笔记 `notes.md`；任务关闭后可以删 |
| `.retro/probes/` | 后台评审 | 探测脚本，评审和侦察报告背后的细节 |

`.retro/` 不进 git，所有分支和 worktree 共用一份，所以委派时写绝对路径。目录里其余的文件由脚本维护，不要手改。总表已经放在别处的，在 PROGRESS.md 里写明位置。

PROGRESS.md 是快照，不是日志：检查点时整体改写，过程细节不放进来。用户指令、待授权、评审结论、换路线、新的最好结果，以及重启之前，随时改对应的那一栏。“目标”一栏和 `/goal` 的条件保持一致，并写明怎么证明（见附表）。

```
# PROGRESS（YYYY-MM-DD HH:MM）
目标（同 /goal）：… · 怎么证明：…
用户指令：- （MM-DD）…
最好结果：…（commit，证据）
路线：… · 押注理由：… · 放弃条件：… · 复查点：…
进行中（名额 N，其中探索 K）：- 任务 — 执行者 / worktree — 占用的资源 — .retro/tasks/<任务>/
下一步（≤5，标出下一个里程碑）：- [ ] …
上次评审：MM-DD HH:MM — 结论 — 采纳 / 未采纳
待授权：- 事项 — 原因（提出 MM-DD HH:MM，已追问 N 次）
其他：手册 RUNBOOK.md · 想法池 .retro/ideas.md · 积压 .retro/backlog.md · 总表 …（汇总命令：…）
```

## 附：Claude Code 和 Codex

| | Claude Code | Codex |
|---|---|---|
| 派任务 | Agent 工具，后台运行（`run_in_background`） | `spawn_agent`，`fork_turns` 设为 `"none"` |
| 追问、让它接着做 | SendMessage | `followup_task` |
| 停掉 | TaskStop | `interrupt_agent` |
| 等结果 | 结束这一轮；子代理交回时会唤醒你，`/goal` 也会定期检查 | `wait_agent`，超时不超过 10 分钟，因为 hook 的提醒只在你调用工具之后送到 |
| 子代理上限 | 默认 20，环境变量 `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` | 默认 3，`~/.codex/config.toml` 里 `[agents]` 的 `max_concurrent_threads_per_session`（不含主线程） |
| 判断目标达成 | 一个独立的模型看对话内容判断，它不跑命令，所以证据要出现在对话里 | 你自己用 `update_goal` 标记完成，标记前要有这次会话里的证据 |
| 一次性提醒 | CronCreate，`recurring: false`；先用 CronList 查有没有 | Codex app 里的一次性线程定时任务 |
| 项目规则文件 | `CLAUDE.md`（里面一行 `@AGENTS.md`） | `AGENTS.md` |
