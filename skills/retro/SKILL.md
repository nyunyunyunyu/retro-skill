# Retro

让长任务持续产生可信的进展，及时发现浪费和方向问题，并能暂停、恢复和接手。主 agent 的注意力留给用户、回报和决定。

有活跃 `/goal` 时，hook 提供计时和状态提醒；目标的开始、暂停、恢复和完成以原生 `/goal` 为准。没有 `/goal` 而用户请求诊断或复盘时，只完成这次请求，不创建目标、不进入持续调度、不启动定时后台评审。停止目标不会从上下文中删除已经读过的规则。

## 职责边界

| 谁 | 负责什么 |
|---|---|
| 主 agent | 用户沟通、理解目标、读回报、短的证据核对、优先级、委派、验收和关键决定 |
| 子代理 | 具体执行、代码、测试、实验、深入探索、读长日志、长程复盘；交回结果、证据和新观察 |
| 脚本 | 记录时间与运行状态、汇总数据、提醒、去重、锁和任务归属检查；执行明确请求的启动或停止 |
| 脚本提醒后由主 agent 处理 | 慢调用、无活动、阶段超时、复查到期、上下文恢复等需要理解任务才能决定的情况 |

**主 agent 保持可响应是硬约束。** 可以直接读摘要、核对少量证据、写简短的进度或任务说明、运行管理命令。一旦需要进入具体问题、连续尝试、大量阅读或长时间推理，就委派；即使某个实现看起来很小，也不要顺手开始。深入的路线复盘同样交给子代理。

没有可用子代理时，说明能力限制，继续处理用户输入和短的只读核对；不要静默切换为主 agent 独自长时间执行。只有一个执行名额也可以推进，评审与执行可以错开。

**判断方式留给你。** 根据目标、证据、成本和资源选择并行度、探索投入、验证范围及是否需要独立评审。保留关键决定的依据，不要求解释每个小动作。

## 要达到的结果

- **用户能控制工作**：新指令和问题在可响应的断点优先处理；问题通常不改变正在推进的目标。区分明确指令与待评估的想法，授权不因转达或提醒而扩大。
- **回报进入决策**：及时接收结果和阻塞；会推翻当前前提的证据优先。不要为了补满名额而延后处理回报。
- **资源用在值得做的工作上**：并行有收益才并行；探索服务于真实的不确定性。空闲名额、少量想法和暂时没有提交，都不能单独证明工作有问题。
- **验证足以支撑结论**：按结果错误的后果选择检查，复用仍然有效的证据。不能通过少测或忽略失败声称加速或完成。
- **方向可以纠偏**：关键假设被推翻、有更好的证据或收益下降时调整；需要独立意见就请求评审。评审提供建议，主 agent 承担路线决定。
- **工作能恢复**：保留目标、用户约束、当前决定、证据、正在做的事和下一步；细节放任务笔记，不塞进主上下文。

## 主循环

开始或恢复时读项目的 PROGRESS.md 和适用规则，用 `status` 核对运行状态。缺少基线、环境或路线信息时，委派摸底，先做不依赖这些答案的工作；不要求固定数量的摸底任务。

日常在这些动作间选择：处理用户输入和回报；决定继续、改派或验收；发出下一项有价值的工作；更新关键状态。没有可做的协调工作时，用平台的等待机制接收事件，不给自己找一个实现任务。

等待采用有界超时，通常不超过 5 分钟，环境要求更短时遵守更短上限。等候结束时处理已经到达的消息和复查事项，不定期打断正常工作的子代理。预计超过约 1 分钟的评测或构建由执行者放到后台，等待期间避开资源和文件冲突。

## 收到提醒

提醒带来的是事实或待检查的信号。先看它是否仍属于当前目标、是否已经处理，再决定继续、补证据、调整、停止或延期复查。只记会影响下一步的决定。

- 慢调用默认在 10 分钟触发；正常可响应时，争取在启动后 20 分钟内完成第一次判断。分析和测量交给执行者，主 agent 决定投入。持续输出不重置计时，正常推进的长任务不因提醒自动停止。见[瓶颈分析](references/bottlenecks.md)。
- 无活动或超过阶段观察时间时，先核对进度和约定；需要打断或重启时，由主 agent 明确决定。底层硬超时和用户停止指令仍有效。
- 检查点是一次简短的整理：读 `inbox` 中尚未处理的结果，更新决定和进度，再用 `done` 标记。需要深入复盘就委派，主 agent 继续响应。可提前整理，不必等提醒。
- 后台评审登记提供一个可选的工作机会；不值得做或资源不足时用 `abort` 释放，不必启动。接受评审时遵守它的登记与交付协议，见[路线与评审](references/review.md)。
- 同一次慢调用默认只提醒一次。选择继续时留下复查时间或条件，由后续主循环处理；当前脚本没有任意复查点的自动调度功能，不要把记录当成已经设好了闹钟。

## 收尾

完成前核对用户目标、必要验证和证据；未完成的事项明确说明。让执行者交回必要结果，停止不再需要的子代理和资源，更新 PROGRESS.md，再给出结果与限制。核实需要深入工作时委派，避免主 agent 在收尾阶段失去响应。

用户要求暂停时先响应，按原生目标机制暂停并安排执行者收尾；不要为了继续整理而延迟叫停。恢复时先读当前目标和现场状态，避免重复启动旧任务。
