# Retro

retro 是 `/goal` 的增强。`/goal` 负责一直推进到完成；retro 让这期间方向不跑偏、想法不断、迭代够快。会话有活跃的 `/goal` 时，hook 会在下面这些时候提醒你；目标结束（达成、判定不可能、暂停、`/goal clear`）后自动停：

| 提醒 | 什么时候 |
|---|---|
| 检查点到期 | 距上次检查点或目标开始满 60 分钟。没做之前每 10 分钟再提醒一次，一轮结束时也会拦一次 |
| 后台评审登记 | 目标开始时登记一次侦察，之后每小时一次评审或侦察；也可以用 `retro.mjs request` 提前要。登记了还没启动的，每 10 分钟再提醒，一轮结束时也会拦一次 |
| 停滞 | 一小时内没有任何新结果时，代替那一轮评审 |
| 名额 | 目标开始 10 分钟还没记下名额；有名额空着超过 5 分钟（从最近一次派任务算起） |
| 子代理异常 | 一段连续跑了 1 小时还没交回；20 分钟没有调用工具 |
| 上下文刚被压缩 | 提醒你重读主循环 |
| 子代理上限太低 | harness 同时允许的子代理数不够，retro 跑不起来 |

提醒里会给出完整的命令，包括脚本路径和 `--root <项目目录>`，照抄就行。下文把它简写成 `retro.mjs inbox` 这样的形式。自己手动运行时，脚本在本 skill 目录的 `scripts/` 下，`--root` 写项目目录的绝对路径（worktree 里的路径会自动换算到主 checkout）。

没有 `/goal` 时也可以按本 skill 手动做，只是没有提醒。用户让你暂停时，如果 `/goal` 还在，提醒用户运行 `/goal clear`（Codex 也可以用 `/goal pause`）。两个工具在用法上的差别见文末附表。

## 术语

- **执行子代理**：做具体工作的子代理，按 `templates/executor.md` 执行和回报。
- **名额**：同时在跑的执行子代理数，不含后台评审。
- **后台评审**：路线评审（`route-reviewer`）或全局侦察（`idea-scout`）。同一项目同一时间只有一个，由 hook 登记。
- **检查点**：主 agent 定时做的整理：收集回报、分流想法、看流动、改写 PROGRESS.md。不改路线。
- **一段**：一次委派从开始到交回或到时间上限，最长 1 小时。接着做算新的一段。
- **验证档位**：探索、采纳、最终三档，决定一个任务验证到什么程度，写在任务说明里（第 3 节）。
- **里程碑**：主 agent 在“下一步”里标出的一批改动的终点，到了就做一次全量验证。一批多大，以全量失败时还能很快找到是哪个改动为限。
- **想法池**：`.retro/ideas.md`，未验证的想法、死路和积压（不急着修的问题）。
- **任务目录**：`.retro/tasks/<任务>/`，放这个任务的回报和笔记。

## 1. 角色

**主 agent 只决策和调度。** 它可以做的事：
- 读回报、PROGRESS.md、想法池、汇总，做必要的只读核对；
- 分派任务、追问、验收；
- 和用户沟通；
- 检查点时改写 PROGRESS.md 和想法池；
- 运行 `retro.mjs`。

代码、实验、测试、深入调查、读长日志，都交给执行子代理，工作量再小也一样。这样主 agent 的上下文才装得下方向。

**用户的输入优先，按类型马上处理，不排队：**
- **指令**（“先做 X”“停掉 Y”）：马上执行。和在跑的任务冲突时，停掉或改派那个任务，并说一句打断了什么。换路线的门槛不适用于用户的指令。
- **想法和观察**（“试试 Z”“这里不对”）：放到想法池最前面，下一个空出来的名额就做，必要时占用探索的名额。你可以给出自己的评估，但照样要试。
- **问题**：直接回答，不打断工作。

其他规则：
- 分不清是指令还是想法时，按指令处理，并说明你的理解，不要停下来等用户澄清。
- 不同意用户的指令时，带着证据说一次，然后照做。不可逆的操作照旧先确认。
- 涉及 `/goal` 本身的，提醒用户自己改。
- 长期有效的指令马上记进 PROGRESS.md 的“用户指令”，不等检查点，免得压缩上下文后丢失。所有代理都必须遵守的规则写进项目的 AGENTS.md（第 8 节）。
- 用户提的事有了结果，告诉用户一声。

## 2. 主循环

不要只在收到提醒时才动。一直按这个循环转：

1. **处理输入**，按这个顺序：用户的话 → 标了“推翻前提”的回报 → 其他回报和继续申请 → 后台评审的结论 → hook 的其他提醒。
2. **补满名额**：有空名额就从“下一步”或想法池派任务，留出探索的份额（第 3 节）。
3. **往前看一步**：在跑的任务交回后做什么？需要提前准备的（拆任务、写任务说明、准备资源）现在就做。
4. **等**：没有可做的事就等结果。不要轮询，也不要自己动手干活。等法见附表；Codex 的等待要设不超过 10 分钟的超时，因为 hook 的提醒只在工具调用之后送到。

**检查点**：提醒到期后，在下一个断点做。几分钟就够，要产出决定。
1. 运行 `retro.mjs inbox`，读上次检查点以来交回的回报、评审和总表。
2. 分流每条观察、想法和发现的问题：放进“下一步”、放进想法池、记成死路、记进积压，或者丢掉。发现的问题按对目标的影响分流（第 3 节“验证”）。
3. 看流动：名额都在用吗，探索的份额够吗？有没有任务超时、卡住、在串行地等、资源在排队？最近的时间花在关键路径上吗？验证（测试、证明、复跑、评审）占了多少，和它保护的东西相称吗？`retro.mjs status` 能看到每个子代理在做什么。
4. 改写 PROGRESS.md 和想法池，格式见第 8 节。
5. 运行 `retro.mjs done`。
6. 在对话里只给一行：“检查点：（做了哪些调整，没有就写不变）”。用户提的事有了结果，另起一句告诉用户。

检查点只在当前路线内调整。觉得路线本身可能有问题，就运行 `retro.mjs request review`（第 4 节）。

**子代理异常**：hook 提醒某个子代理超时或长时间没动静时，问它一次进展。没有说得过去的理由，就停掉它，按它任务目录里的 `notes.md` 另派。

**目标结束时**（达成、判定达不到，或用户叫停）：在宣布达成之前做完下面这些。Claude Code 在你结束最后一轮、没有后台任务时判定目标，判定达成后你就没有下一轮了；Codex 要在调用 `update_goal` 之前做完。
1. 停掉所有在跑的子代理，包括后台评审；
2. 达成时按最终档位验证一次（第 3 节），新的最好结果要核实过才算数；叫停或判定达不到时不跑，报告里写明验证到了哪一档；
3. 把 PROGRESS.md 改成最终状态：结果、证据、没做完的事；
4. 清理不再需要的 worktree 和占着的资源；
5. 给用户一份简短的最终报告，附上积压里还没修的问题。

## 3. 委派和回报

**名额**在目标开始时定下来，取下面三项的最小值：
- 资源允许的数量：只有一个游戏实例、一块 GPU 就少开，不抢资源的工作可以多开；
- 用户在 `/goal` 条件里写的上限，比如“最多并行 4 个”；
- harness 的子代理上限减 3：1 个留给后台评审，2 个留给临时的核实和追问。上限的默认值和设置方法见附表。

定好后运行 `retro.mjs slots <N> <理由>`，资源变了就重新运行。hook 靠这个数检查名额有没有空着。上限减 3 后不到 2 个名额时，hook 会让你先停下，请用户调大设置。

**探索的份额**：默认大约三分之一的名额用来验证想法池里的想法，其余推进主线。主线进展顺利时少一点，连续几轮没有提升时多一点。

**任务说明**，每次委派都写清：
- 任务、目标和验收标准、范围；
- 相关的用户指令；
- 已知的事实和死路，从想法池和以前的回报里摘，免得重走；
- 时间上限：一段不超过 1 小时，更大的活拆成几段；
- 验证档位和验证的时间预算（见下文“验证”；评审和核实类的任务只给预算）；
- 可用的资源（核数、内存、GPU）和不能碰的东西；
- 任务目录 `.retro/tasks/<任务>/`，写绝对路径。

最后加一句：“开始前先读 `<本 skill 目录>/templates/executor.md`，按其中的规则执行和回报。”

每个任务都从新的上下文开始，不继承你的对话，所以任务说明本身要写全。代码地图这类通用背景放进手册（第 8 节），任务说明里指过去就行。

**收到回报后**：
- **先补位**，再处理内容。
- **标了“推翻前提”的马上处理**：调整下一步，叫停相关的任务。
- **新的最好结果，采纳前先核实**：另派一个子代理在干净的环境里复现。评测是确定性的（比如固定种子）时，复现只能证明可重复，复现一小部分就够，重点让它审一遍评测本身：规则、统计方法、有没有漏算的情况。
- **值得探讨的观察和想法**：继续问原来那个子代理，它还保留着上下文。问清证据、反例和细节，然后明确结论：采纳、暂缓、否决，或者做一个轻量验证。小的验证就交给提出它的那个子代理。不是每条都要讨论；讨论也不能绕过换路线的门槛。
- **其余的**：留到检查点统一分流。

**继续申请**：子代理到了时间上限会停下，交阶段回报和继续申请：还差什么、实测的进展、再要多久。由你决定：
- **让它接着做**（默认）：上下文还在，最便宜。给它新的时间上限，算新的一段。
- **换一个新的子代理接手**：原来的上下文已经很乱，或者方向要变。任务说明里带上它的 `notes.md`。
- **停掉**：进展不值得再投入。

**中途找你**：子代理只在前提不成立、出现新的最好结果、被阻塞、验证要明显超出预算、发现了影响别的任务的事时，交一份标了“中途”的简短回报。处理完让它接着做。不要定期去问进展；超时和没动静的子代理 hook 会提醒你。

**验证**：投入要和它保护的东西相称，看两点：结论错了代价多大，错的可能多大。为一个探索性的想法跑几小时全量，或者一遍遍加固已经审过的测试，都是在浪费迭代时间。每次委派写明档位，以及最多花多少时间在验证上：
- **探索**：能判断这个想法值不值得继续的最便宜的信号，比如冒烟测试、子集、几局。错了只是多试或少试一个想法。
- **采纳**：合进主线或采纳新的最好结果之前。只查这次改动可能弄坏的部分，比如相关的测试、针对性的评测；新的最好结果另外核实（见上文）。
- **最终**：目标达成或到了里程碑，全量跑一次。超过一段的时间上限，就按分片拆成几段。

另外：
- 用户明确要求的验证照做，其余的按档位来。
- 同一套全量验证只跑一层：执行子代理在干净的环境（新的 clone 或 worktree）里跑过的，核实时不再整套重跑，只看证据、审评测本身。例外是有随机性的评测，新的最好结果要独立复现。
- 机械性的改动（搬代码、改名、按固定模式重构）每个任务只跑快速检查，攒到里程碑统一跑一次全量。
- 测试、对比脚本、评测这类验证工具，审过一次就冻结它检查得多严。之后只在它放过了真实的错误时才修，构造出来的变异或假设的情形不算；不因为“还能更严”再开加固任务。让它跑得更快不受限制，按第 6 节先和旧版对齐。
- 评审和核实发现的问题，回报里每条都写明对目标的影响，按影响分流：
  - **高**：不修，目标的结果就会错或者达不到。马上派任务修。
  - **中**：值得修，但不改变结论。合进相关的任务顺手修，或者记进积压，到下一个里程碑一起修。
  - **低**：记进积压，主线和探索都没事可做时才修。

## 4. 路线：评审和侦察

检查点只在当前路线内调整：重排“下一步”，记下新发现。换路线、大调优先级，交给后台的路线评审。唯一的例外：路线事先写好的放弃条件已经明确触发，就换到想法池里排第一的备选路线，并给新路线写上放弃条件和复查点。

后台评审在同一个项目里同一时间只有一个，由 hook 登记：
- **全局侦察**（`idea-scout`）：在目标刚开始时、距上次侦察满 4 小时时，或想法池里未验证的想法少于 3 条时登记。它从全局出发找想法和知识缺口，只提不拍板。
- **路线评审**（`route-reviewer`）：其余时候每小时一次。它对照想法池拍板：保持、调整优先级、先探测，还是换路线；也看流动和迭代速度。
- **提前要一次**：觉得路线可能有问题，或者想法池空了，运行 `retro.mjs request review` 或 `retro.mjs request scout`。正在跑一轮时，它结束后马上登记。

**启动**：收到“已为你登记”的提醒后，在下一个断点于后台启动对应的子代理，提示照抄提醒里那句话。登记后要在 20 分钟内启动。启动这件事 hook 会自己记下，子代理开始时也会再标记一次，你不用写任何文件。启动失败就运行 `retro.mjs abort <开始时间>`。启动后不要等它。

**超时**：从启动算起，评审限 20 分钟，侦察限 40 分钟，超时后 hook 会把这一轮作废。提醒你停掉它时，能停就停。

**收到结论时**：先补位，再对照报告里的依据看当前状态。如果评审开始之后的新结果已经推翻了它的前提，结论只当参考。侦察给出的想法放进想法池。评审的结论按类型处理：
- **调整优先级、先探测**：有证据支持才采纳，采纳了就重排“下一步”。
- **换路线**：复查点之前，只有放弃条件触发才换，否则记为备选。新路线的收益要明显超过切换成本，并且有证据；换了之后写上新的放弃条件和复查点。
- **推翻上次评审的结论**：需要新证据。
- **流动和迭代速度的建议**：按第 6 节的 ROI 决定做不做。
- **涉及 `/goal` 本身**（目标达不到或设错了）：只提给用户。

最后在 PROGRESS.md 的“上次评审”里记一行：时间、结论、是否采纳。对报告有疑问，可以继续追问原来的评审代理。

没有子代理功能时，检查点时自己花两分钟按同样的问题看一遍路线，只调整优先级，不换路线。

## 5. 想法池

想法池是 `.retro/ideas.md`，未验证的想法最多 15 条，按价值排序，价值低的直接删掉：

```
## 想法
- [ ] 想法 — 来源（用户 / 任务名 / 侦察 / 评审）— 预期收益 — 最便宜的验证 — 成立标准
- [~] 正在验证的想法 — 任务名
## 死路
- 方法 — 原因（日期）
## 积压
- 问题 — 来源 — 影响（中 / 低）— 怎么修
```

用户提的想法排在最前面。探索的名额从池子顶部挑一条，按“最便宜的验证”去做，限定时间，事先写好成立标准。验证成立的想法成为采纳候选，放进“下一步”或作为备选路线；不成立的移进死路。

积压放评审和核实发现的、不急着修的问题（第 3 节“验证”），不算在 15 条里，所以不加 `[ ]`。每条一行，同类的合并。

- 池子空了：运行 `retro.mjs request scout`，同时自己从失败归因里想出 3 个机制不同的想法。
- 连续几轮没有提升：同样处理，并问自己“如果当前路线被禁止，我们会怎么做？”

## 6. 迭代速度

一轮迭代越快，同样的时间里能试的想法越多。先测量再优化：派执行子代理实测一轮迭代里各部分的耗时（评测、读输出和改代码、日志进上下文的量），只优化瓶颈。便宜的手段先上：评测只打印摘要、一键运行、缓存、并行。用子集做代理评测前，先验证它和全量评测的排序一致。评测代码本身往往是最大的杠杆，比如 30 秒的 CPU 循环搬到 GPU 上只要 0.1 秒。

做不做，按 ROI 判断，不套公式，相信你自己的判断：
- 收益按整个目标剩下的时间算，不只是当前这个任务；加速如果能解锁新方法（扫参、搜索），也算进去。
- 成本按你乐观估计的两倍算，再加上校验正确性的时间。
- 收益明显就做；拿不准就先做最便宜的一步，看效果再说；不要为了快而过度优化。
- 快版本先和旧版本的结果对齐，再替换。

**评测分层，便宜的先跑。** 按耗时把检查分成几层：几秒的（编译、静态检查、最小的冒烟测试）、几分钟的（相关的测试、子集评测）、全量。跑到哪一层由验证档位决定（第 3 节）。每次从最便宜的层开始，失败就先修，不往更贵的层跑。各层的命令写进手册的 `eval.md`；手册只写怎么跑，不规定每次都跑全量。
- **尽早失败**：长评测先用最小的规模试跑一遍，确认整个流程能走通；最容易出问题的部分（最大的输入、刚改过的地方）排在前面；拆成分片，每片有自己的超时，一片失败马上报出来，重跑时只跑失败的那片。不要让几小时的任务到最后才失败。
- **用满机器**：跑长评测时看一眼 CPU、内存、GPU 的实际占用。只用了一小部分核的，并行往往是最便宜的加速；内存不够就降低并发或者缩小分片，不要等到崩溃。

不要空等：超过约 1 分钟的评测或构建放到后台跑，同时安排不冲突的工作。不要改正在跑的任务依赖的文件，要改就在副本或 worktree 里改；不要同时跑抢同一块 GPU、CPU 或同一个游戏实例的任务。

长时间没有结果，本身就是迭代太慢的信号。资源在排队时，其他名额去做不占这个资源的事（离线分析、单元测试、回放），并考虑增加资源，或者做一个更快的代理评测。

## 7. 等待与授权

需要用户授权才能继续时，不要停下来干等，也不要用会一直阻塞的方式提问：
1. 在 PROGRESS.md 的“待授权”里记一行，在回复里提一次，然后继续调度不依赖它的事。
2. 没有答复的，满 30 分钟和满 2 小时时各合并再问一次，之后不再追问。

只在等用户时，`/goal` 不会唤醒你，所以要自己设提醒。记下事项时，先查有没有待触发的追问提醒。没有的话，建两个一次性提醒，分别在 30 分钟后和 2 小时后，一次覆盖所有待授权事项（工具见附表；没有定时工具，就只提这一次）。

提醒的提示词：“[retro 待授权追问] 如果 PROGRESS.md 的‘待授权’里还有没答复的事项，合并成一条再问用户一次，然后继续调度不依赖它们的事；都答复了，或者 /goal 已经结束，就什么都不做。”

## 8. 文件

| 文件 | 谁写 | 什么时候写 | 内容 |
|---|---|---|---|
| `PROGRESS.md`（项目根目录） | 只有主 agent | 检查点时整体改写；记用户指令、待授权、评审结论，换路线、出现新的最好结果、重启前，随时改对应的那一栏 | 方向快照，不超过 4 KB，模板见下 |
| 手册：`RUNBOOK.md` 和 `runbook/`（跟代码走，每个分支一份） | 谁改了运行方法谁改 | 构建、测试、评测的方法变了时 | `RUNBOOK.md` 只做索引，不超过 1 KB：每个子文件一行，写明什么时候该读。具体内容放在 `runbook/` 下，比如 `build.md`、`eval.md`、`code-map.md` |
| 项目的 `AGENTS.md` | 主 agent 交给执行子代理写 | 出现所有代理都必须遵守的规则时 | 全局规则和所有任务都会踩的坑。`CLAUDE.md` 里只写一行 `@AGENTS.md`，两个工具读同一份 |
| `.retro/ideas.md` | 主 agent | 检查点时 | 想法池、死路和积压 |
| `.retro/results.tsv` | 评测脚本 | 每次标准评测 | 影响决策的数字，一次评测一行：时间、任务、commit、指标、值、样本数、失败类别、证据位置；不手抄数字 |
| `.retro/tasks/<任务>/` | 执行子代理 | 任务进行中 | `report.md`（必须有）、`notes.md`、`data/`；任务关闭后可以删 |

坑写在会踩到它的地方：所有任务都会遇到的，写进 AGENTS.md；只在某个流程里遇到的，写进手册里那个流程的子文件。

`.retro/` 由 hook 创建，自带 `.gitignore`，不进 git。所有分支和 worktree 共用这一份，所以委派时要写绝对路径。目录里其余的文件（`slot`、`slots`、`retro-done`、`log.tsv`、`sessions/`、`reviews/`、`user-inbox.jsonl`、`user-said.md`）由脚本维护，不要手改。已有项目的总表如果放在别处，在 PROGRESS.md 里写明位置就行。

PROGRESS.md 是快照，不是日志：每次改写，不追加；过程细节不放进来。“目标”一栏和 `/goal` 的条件保持一致，并写明怎么证明（两个工具判断达成的方式不同，见附表）。

```
# PROGRESS（YYYY-MM-DD HH:MM）
目标（同 /goal）：… · 怎么证明：…
用户指令：- （MM-DD）…
最好结果：…（commit，证据）
路线：… · 押注理由：… · 放弃条件：… · 复查点：…
进行中（名额 N，其中探索 K）：- 任务 — 执行者 / worktree — 占用的资源 — .retro/tasks/<任务>/
下一步（≤5，标出下一个里程碑）：- [ ] …
上次评审：MM-DD HH:MM — 结论 — 采纳 / 未采纳
待授权：- 事项 — 原因（提出 MM-DD HH:MM，已追问 N 次）
其他：手册 RUNBOOK.md · 想法池 .retro/ideas.md · 总表 …（汇总命令：…）
```

## 附：Claude Code 和 Codex 的差别

| | Claude Code | Codex |
|---|---|---|
| 派任务 | Agent 工具，后台运行（`run_in_background`） | `spawn_agent`，`fork_turns` 设为 `"none"` |
| 启动后台评审 | Agent 工具，`subagent_type` 填 `idea-scout` 或 `route-reviewer`，后台运行 | `spawn_agent`，`agent_type` 填同名，`fork_turns` 设为 `"none"` |
| 追问、让它接着做 | SendMessage | `followup_task` |
| 停掉 | TaskStop | `interrupt_agent` |
| 等结果 | 结束这一轮；子代理交回时会唤醒你，`/goal` 也会定期检查 | `wait_agent`，超时不超过 10 分钟；子代理交回的结论只在你活动时送到 |
| 子代理上限 | 默认 20，环境变量 `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` | 默认 3，`~/.codex/config.toml` 里 `[agents]` 的 `max_concurrent_threads_per_session`（不含主线程） |
| 判断目标达成 | 一个独立的模型看对话内容判断，它不会自己跑命令，所以证据要出现在对话里 | 你自己用 `update_goal` 标记完成，标记前要有这次会话里的证据 |
| 一次性提醒 | CronCreate，`recurring: false`；先用 CronList 查有没有 | Codex app 里的一次性线程定时任务 |
| 项目规则文件 | `CLAUDE.md`（里面一行 `@AGENTS.md`） | `AGENTS.md` |
